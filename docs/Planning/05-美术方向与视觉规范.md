# VoxalBlast 美术方向与视觉规范

> 版本：MVP v0.2.29
> 负责人：美术
> 参考方向：CrazyGames 上的 Block Blast 类产品
> 风格定位：更还原 Block Blast 的卡通休闲气质，同时保留 VoxalBlast 的 3D 玩法差异
> 协作约定：所有后续美术、UI、字体、镜头、动效和宣传素材修改，必须同步更新本文档后再落地实现

## 1. 方向结论

VoxalBlast 采用“Block Blast 式卡通休闲益智”作为第一视觉印象：明亮、圆润、轻松、正向、容易理解。玩家进入游戏时，首先感受到的应是彩色积木和爽快消除，而不是复杂的 3D 技术展示。3D 只服务于玩法——帮助玩家旋转、观察和放置——不改变整体的卡通亲和力。

参考 [Block Blast Master](https://www.crazygames.com/game/block-blast-master) 等 CrazyGames 上的 Block Blast 类产品，其核心视觉特点是高明度彩色方块、简洁背景、清晰网格、柔和立体感、醒目的分数反馈和积极的消除奖励。VoxalBlast 将这些特点作为基线，同时把二维棋盘改造成可旋转的 六面体(每面 5×5) 立体棋盘。

VoxalBlast 不复制具体页面、Logo、角色或素材，而是复用同一类视觉语法：大色块、软倒角、干净轮廓、浅色底板、轻量阴影和有节奏的庆祝动效。品牌识别度来自“三维方块空间 + 三轴连线消除”，而不是来自复杂装饰。

关键词：**Block Blast 式卡通、明亮正向、圆润积木、软阴影、清楚轮廓、三轴连爆**。

## 2. 视觉目标

- 首屏一眼识别：棋盘是主角，方块是可操作物，分数和重开入口保持在外围。
- 颜色承担分类，不承担唯一的信息表达；轮廓、明暗和占格预览必须同时有效。
- 方块看起来像规则制造的塑料积木，而不是写实材质、玻璃、金属或随机生成的 3D 资产。
- 消除反馈有节奏但不喧宾夺主：固定、确认、消除、得分四个阶段清楚可读。
- 画面保持轻快和耐看，长时间游玩不依赖强光晕、噪点或满屏粒子制造刺激。

## 3. 当前实机偏差审查与重构结论

用户提供的竖屏图是当前实现效果，**不作为目标界面基线**。它只能用于定位问题和验证重构前后差异。当前效果与 Block Blast 的差距属于视觉体系偏差，不是换色或增加圆角即可修复。

### 3.1 当前实现的主要问题

- **主视觉错位**：大面积半透明 3D 线框占据画面中心，第一眼像建模工具或科技演示；目标应让彩色积木和可放置格子成为第一视觉主体。
- **颜色面积失衡**：背景、面板、棋盘和按钮都集中在相近的蓝色区间，彩色方块面积过小；目标应形成“浅亮背景—深色棋盘—大面积高饱和方块”的明确三级关系。
- **UI 过度工程化**：`CURRENT RUN`、`VOXEL GRID`、编号、版本号、轴向文字和细线分隔过多，形成仪表盘感；Block Blast 类产品应少文字、强数字、强图形、强按钮。
- **玻璃科技感过强**：全屏半透明卡片、细描边、冷色辉光和一致透明度让界面显得薄、冷、克制；目标应是厚实圆润的卡通面板和玩具按钮。
- **棋盘可读性不足**：空棋盘用完整立方体笼状线框表达，线条重叠后无法快速判断层级、落点和有效操作面。
- **候选块存在感不足**：三个候选块缩在半透明卡片顶部，名称和编号反而更突出；目标应让方块预览占卡片 65%～75%，文字退居辅助或直接移除。
- **情绪不匹配**：当前氛围偏冷静、科技、实验；目标是活泼、温暖、积极、具有即时奖励感。
- **网页感仍然明显**：画面留白过大，内容像网页 Banner；棋盘、分数和候选块没有形成完整的游戏场景。
- **文字不像游戏**：文字过小、过细、过淡，英文全大写标签和较大字距形成数据面板感，不能提供休闲游戏应有的即时反馈和情绪。
- **信息密度分配错误**：说明性文字抢占了空间，但真正重要的分数、方块和操作反馈不够突出。

### 3.2 本轮整改结论：从网页 Banner 改为游戏 HUD

本轮以用户提供的横版实机截图为整改依据，不再增加背景装饰，先重做文字、比例和游戏主体：

- 删除 `VOXEL GRID`、`VIEW ADJUSTED`、长说明段落、候选块编号和 `VOXELS` 数量等非必要工程信息。
- `SCORE` 只作为小型辅助标签，当前分数使用大号、厚实、圆润的展示字体；不再显示 BEST / LINES 等统计。
- `PIECES` 改为 `NEXT` 或直接隐藏；候选块名称默认隐藏，只有无障碍或悬停提示需要时才提供。
- 版本号退出主界面；设置、重开等功能保留为小型图标按钮。
- 3D 棋盘和候选方块放大约 1.5～1.8 倍，减少无意义的蓝色留白，让画面打开后立即像可以操作的游戏。
- HUD 叠加在游戏场景上，不使用网页式多列面板、长分隔线和卡片列表；候选块改成底部游戏工具栏。
- 字体使用圆润、厚实、偏胖的卡通游戏字体；优先 `Nunito`，无外部字体时使用 `Arial Rounded MT Bold`、`Trebuchet MS` 降级。避免细体、窄体、等宽体、未来感字标、全大写小字和过度字距。
- 消除高光降低白色过曝，使用亮黄闪光、彩色小方块、星星和分数弹跳表达奖励。

验收标准：截图缩小到 240px 宽后，第一眼看到的是彩色积木和 3D 棋盘；即使隐藏全部文字和按钮，画面仍应像一个完整的休闲游戏场景，而不是网页 Banner 或数据面板。

### 3.3 必须保留的功能结构

- 当前分数与消除反馈数字。
- 中心 六面体(每面 5×5) 棋盘及视角环绕/缩放观察能力。
- 三个固定朝向的候选方块槽位。
- 视角环绕与缩放观察能力（方块不提供旋转，镜头不提供复位）。
- 单一设置入口，设置面板提供声音、触感与重新开始。

保留的是这些功能，不保留当前玻璃仪表盘式的表现形式。

### 3.3 重构后的目标画面

- 顶部为一条紧凑信息栏：左侧 SCORE 积分胶囊、右侧单一设置图标；开发版版本号以正中小徽标悬浮（脱离布局流，正式版移除时不影响 SCORE/设置位置）；不显示游戏名/Logo，棋盘可占满下方主要可视区。
- 3D 操作区域占可玩画面的 60%～70%，去掉突出的圆角场景底板和棋盘实体底座，让 六面体(每面 5×5) 待填充空间直接悬浮在天蓝背景上，优先保证完整显示。
- 保留少量空间锚点：外框八角/关键边、最底层投影格面、当前活动层和落点预览；不再显示完整笼状全空间线框。
- 开局即通过示意块、短引导或更清楚的活动格面避免中央区域空洞；玩家应看到“悬浮的可填充积木空间”，而不是空坐标系。
- 三个候选块使用轻量半透明卡槽，槽内显示裸 3D 方块组合（复用棋盘圆角几何、统一光照与材质明暗），预览放大、弱化文字，整体贴近 Block Blast 的"悬浮裸形状"观感。
- 候选预览保持斜 3/4 视角，必须能看出顶面、侧面和体积厚度；预览视角随主棋盘绕世界 Y 轴同步转向，使方块在槽位与落子处朝向一致，不提供独立旋转操作。
- 界面文案向休闲游戏收敛：只保留大号 SCORE 与必要按钮；删除 VOXEL GRID、BEST、LINES、VIEW ADJUSTED、说明段落、候选块编号和 VOXELS 等工程化信息；减少全大写小字与过宽字距，采用圆润、厚实、偏胖的卡通字型。
- 道具图标行（换批 / 锤子 / 火箭 / 炸弹）置于棋盘下方候选方块之下，采用圆形程序化图标与数量角标，与现有 UI 图标同源。
- 整体压缩留白、放大 3D 棋盘与候选方块预览，让高饱和彩色积木成为第一视觉主体，画面不再像数据面板或网页 Banner。
- 不提供方块旋转控件（X/Y/Z 按钮与 WASD 方块旋转已移除），也不提供镜头复位（VIEW RESET / R 键已删除）。
- 背景使用天蓝到浅蓝的柔和渐变，可有低对比云雾和极少星点，但不抢棋盘。
- 消除时使用亮黄闪光、彩色小方块、星星和分数弹跳，建立 Block Blast 式积极奖励。

### 3.4 重构优先级

1. 移除中间圆角场景底板和 3D 棋盘实体底座，重做悬浮空间表达，并删除完整笼状线框。
2. 调整镜头距离、视野角和安全边距，保证默认及旋转后的 六面体(每面 5×5) 空间完整显示。
3. 放大彩色方块在首屏中的面积，并提高圆润、厚实和玩具感。
4. 去掉大部分工程化标签、编号、说明文字和玻璃分隔线。
5. 重做候选方块卡槽与底部视角操作区。
6. 最后添加云雾背景、庆祝粒子和轻量装饰。

验收原则：如果把游戏截图缩小到 240px 宽，仍应先看见“彩色积木游戏”，而不是“蓝色 3D 网格工具”。

## 3.5 v0.2.21 实施记录：Banner 与棋盘可读性

本轮针对竖屏实机反馈“上部 Banner 偏薄、棋盘方块看不清、整体不卡通”完成第一轮参数化调整：

- 顶部信息栏增加白色内高光、柔和底部投影和更明确的 SCORE 积分胶囊边界；分数数字加粗并提高字号，避免与天蓝背景混在一起。
- 棋盘区域增加低对比椭圆泛光作为舞台光，不增加硬边底板或新装饰，帮助彩色积木从背景中分离。
- 圆角方块几何从 `0.86` 放大到 `0.92`，倒角从 `0.075` 提高到 `0.105`，使方块更像圆润的塑料玩具。
- 方块材质改为更哑光、更不透明的高饱和色，降低自发光与金属感；统一主光方向，避免边缘过曝。
- 移除每个方块上的白色强线框，改用深蓝低透明度轮廓配合倒角和明暗面表达体积，解决手机尺寸下线框重叠导致的“看不清”。
- 落点候选由立体线框改为低透明度亮绿薄格面，保留玩法提示但不与已放置方块争夺视觉层级。

本轮不增加背景插画、纹理和粒子。验收重点是：缩小到手机实际尺寸后，先看到高饱和圆润积木，再看到棋盘空间提示；顶部 Banner 与棋盘主体形成“白色 HUD—天蓝舞台—彩色玩具”的清晰层级。

### 3.6 v0.2.23 实施记录：悬浮空间棋盘（去实体化，方块成为体积主体）

针对实机截图“实体深色体块 + 六面全网格 + 完整外框让方块像嵌入墙面”的反馈，重构棋盘渲染层级，目标为「彩色方块 > 棋盘空间边界 > 背景辅助光」：

- **移除整块实体立方体**：`cubeBody` 由不透明圆角实体改为近不可见的深海军蓝空间色调（`hullOpacity 0.05`、去自发光、`depthWrite:false`），仅保留空盘时对 5×5×5 空间范围的微弱暗示，不再形成“深色方盒”视觉主体。
- **网格线全面弱化**：六面 N×N 网格线不透明度从 `0.3` 降至 `0.13`，颜色转浅；网格只负责格位暗示，不负责构成棋盘主体。
- **外框笼退化**：12 棱空间边界不透明度从 `0.2` 降至 `0.11`，作为“少量可见空间边界”，不再像完整玻璃容器/工程线框模型。
- **方块从表面浮出**：已放置方块沿其所在外壳的径向方向外凸 `0.17` 晶格单位（棱/角格沿对角外凸），方块与方块保留约 8% 的稳定缝隙；落子预览与道具覆盖层使用同一外凸定位，所见即所得。
- **材质去自发光**：方块材质去掉“同色自发光 + 微光”，改回纯物理光照（粗糙度 0.46），顶面高光与侧面压暗完全由统一主光产生，避免“发光贴墙”感。
- **取景放大与居中**：PC 安全系数 `0.88→0.97`、移动端 `0.82→0.93`，棋盘在中央操作区更大；PC 中心微降、移动端中心上移（`targetY`），压缩“深色小立方体 + 大量留白”的观感。
- **悬浮软影锚点**：棋盘下方叠加低透明羽化椭圆软影（`::after`，宽不超过投影宽 65%、全羽化），空盘也呈现“悬浮可填充空间”，不构成新硬边底板。

参数全部集中在 `src/rendering/config.js` 的 `BOARD_STYLE` 中，`main.js` 只消费常量。

### 3.7 v0.2.24 实施记录：5×5×5 尺度与旋转停稳

棋盘从 6×6 六面缩到 **5×5 六面（5×5×5 晶格）**，并同步重做旋转停稳手感：

- **尺度收敛**：`board.js` 的 `SH` 由 6 改为 5，六个面各为 5×5；立方体边长、格线、外框、相机取景、道具作用域（火箭整行/列、炸弹 2×2）全部由 `SH` 派生，无需另行改数。
- **形状池同步**：面变窄后 5 格直线只能落在完全空白的行/列上并立即成线（白送分数、几乎废掉 Game Over），故从 12 类缩为 **11 类**，最长直线改为 4。
- **停稳姿态**：旋转后必定有**一个面正对玩家**，并保留偏航/俯仰每轴 ≤8° 的轻微偏摆，既让放置面干净可读，又不会让立方体在读图时塌成一张平面；**Z 自转不留偏摆（v0.2.26 起）**，自转必须精确落回 90° 网格，否则玩家看到的是"歪着的面"。
- 参数集中在 `src/rendering/config.js` 的 `ROTATE_STYLE`（方向符号/阈值/偏摆上限/吸附时长与回弹量），`main.js` 只消费常量。

### 3.9 v0.2.26 实施记录：Z 自转归正、候选朝向不跟立方体转

- **Z 自转归正**：`restOffsetRoll` 由 `0.14` 改为 `0`，自转停稳后不再出现歪斜的面；弹性手感改由停稳动画的轻微回弹提供（`snapOvershoot = 1.05`，约 4% 越过后回弹到目标姿态，最终姿态仍精确是计划值）。
- **候选方块朝向不跟立方体转**：新增 `faceOrientedCells()`，把候选的 (u,v) 重新表达为"当前正对玩家的面"上对应**屏幕右 / 屏幕上**的两个面内轴（每帧按相机右/上向量投影到该面求出）。中立姿态下映射退化为恒等，与旧行为逐格相同；绕 Z 自转 90° 后，方块在面上呈现的朝向与候选槽位显示一致，**方块不再随立方体转动而转动**（此前会跟着转 90°，属缺陷）。放置时直接使用预览算出的格子（`drag.cells`），保证"看到的即落下的"。
- **Game Over 判定同步放宽**：立方体 6 面 × 4 个平面内朝向都可达，`Board.anyPlacement()` 按 4 个平面内朝向判定，避免只差一个侧向朝向能放时误判。
- ⚠️ 本轮还整体取反了三轴方向（误判"方向反了"），v0.2.27 已撤销，见下。

### 3.10 v0.2.27 实施记录：手势轴固定在世界坐标（修掉"轴跟着立方体转"）

- **问题**：v0.2.25~v0.2.26 把姿态存成三个欧拉分量并按固定序 `Rz·Ry·Rx` 合成，于是**一个手势的实际转轴会被另外两个角带动**：偏航 90° 后，`Rz·Ry·Rx` 里的 pitch 增量实际绕的是世界 Z，于是"上下滑动"变成了平面内自转，正对的面根本不变；自转 90° 后，yaw 增量实际绕世界 -X。玩家读到的是"XY 轴跟着六面体一起转了"，并因此误判成"方向反了"。
- **改法**：手势轴**固定在世界坐标**（偏航=世界 Y、俯仰=世界 X、自转=世界 Z），每次手势先停稳、再以当前姿态为基准绕该固定轴转；网格姿态改用**四元数 `cubeBase` 累乘整 90° 台阶**（永远在 90° 网格上、不会漂移），≤8° 的偏摆单独放在 `cubeRest*`，渲染姿态 = 偏摆 ∘ base；停稳动画改为**四元数 slerp + easeOutBack**（自转因此精确归正，动效仍有回弹）。
- **方向回到"跟手"**：右滑正面往右走、六面体范围内下滑正面往下走、窄带下滑顺时针自转（v0.2.26 的整体取反撤销，方向值仍在 `ROTATE_STYLE.*Direction`）。
- **俯仰限位**：俯仰是唯一能翻过极点的轴——正面对着赤道面时允许翻一格，已到顶/底面后只允许往回翻（等价于旧版"俯仰角限位 ±90°"）。**⚠️ 该限位已在 v0.2.30 撤销：见 3.13。**

### 3.12 v0.2.29 实施记录：修掉"有些时候转不动，像锁住了"

三条真实缺陷都会表现为"这一下白滑了"。修复只动**手势的识别与标尺**，单次手势的姿态语义（固定世界轴、一次最多翻一面、俯仰限位、Z 自转归正）完全不变（其中"俯仰限位"已于 v0.2.30 撤销，见 3.13）：

- **定轴只看起手 6px → 误判轴并吞掉整段手势**：手指起手常带几像素侧向抖动，按起手 6px 处的位移定轴会把一次上下滑判成"偏航"；而"已定轴的手势忽略另一轴"，随后 200px 的竖直位移完全不驱动任何轴——六面体一动不动，玩家读成"锁住了"。改为**领先方向必须明确领先**（`axisDominance = 1.2`）且位移过 `axisLockPx = 16px` 才定轴，一直不明确则由 `axisHardLockPx = 44px` 兜底判定给领先者；定轴前每帧重判、定轴后不再切换（仍满足"单次手势只认一个轴"）。
- **拖动→角度的标尺是画布尺寸 → 桌面端一次翻面要滑 185px**：`dx / canvasWidth * π` 让"约 30° 阈值"在 390px 手机上只要 65px、在 1120px 桌面画布上要 185px，桌面上正常的一滑经常直接弹回（"有时候转不动"）。标尺改为**六面体自身在屏幕上的投影尺寸**（定轴时采样一次），两个轴、所有视口统一为"滑约 1/6 个六面体 = 翻一面"。
- **丢失 pointerup 会让旋转永久失效**：页面隐藏、窗口失焦、触摸被浏览器手势抢走时浏览器不再补发 `pointerup`，`viewDrag` 残留后 `beginViewDrag()` 从此拒绝任何新手势——旋转彻底锁死，而放置照常可用（正是"只有旋转锁住"的观感）。新增 `cancelViewDrag()`：`visibilitychange`（隐藏）、窗口 `blur`、Reset 结束手势并把中途姿态停稳；按下时若发现旧手势的指针捕获已丢失，也会先回收再开始新手势。
- **实现与验证**：定轴 / 标尺 / 角度三个纯函数移到 `src/rendering/swipe.js`（无 DOM、无 three），`main.js` 只负责事件与姿态应用；`.tmp/probe-swipe.mjs` 直接调用真实模块复跑 8 条用例（起手抖动路径、115px 横滑、手机视口同类滑动、短滑弹回、斜向兜底、俯仰限位、窄带自转、同路径在旧规则下确实为死滑），8/8 通过。本机浏览器无法在非交互会话中启动，动作手感仍需在 GUI 里手动过一遍。

### 3.13 v0.2.30 实施记录：松手不再吞掉手指已经划出来的旋转

- **问题（玩家报"在中心区域上下滑动，松手前是转动了，松手后会弹回去"）**：手势进行中的姿态是**自由跟手**的（角度不设上限），松手时才判定"最多翻一个面"，两条路径不一致，于是出现了两种"白转一场"：
  1. **俯仰限位**：正面已经到顶/底面后，同一方向的下一格被拒（`stepped = 0`）。手指明明把六面体转过去一整面（连背面都露出来了），松手却整段收回，而且**该方向此后永远无效**。
  2. **拖动超过一个面**：`startCubeSnap()` 里 `rest` 被 clamp 到 ±8°，超出一个面的部分在停稳时被反转回来。
  真实构建探针实测（1440×900）：**重复下滑 拖动 105.5° → 松手弹回 89.5°**；**一次长滑 拖动 136.4° → 松手少 38.4°**；第三次同方向下滑步进 `0.0000°`。
- **改法**：①**删除俯仰限位**及其 `pitchReach` 记账——固定世界轴 + 四元数网格姿态下它已无保护对象，翻过极点只是普通的下一格（`+z → +y → −z → −y → +z`）；②`setLiveAngle()` 把**渲染角度** clamp 在"起手姿态 ± `ROT_STEP`（一个面）"内，使**手势中看到的旋转量 = 松手后兑现的量**；③`startCubeSnap()` 直接使用 `planAxisStep()` 返回的 `stepped/rest`，删掉为配合限位而重复计算的 `rest`。
- **保留的行为**：未过阈值（≈30°）的短滑仍然弹回起手面（"轻点不翻面"），Z 自转仍然精确归正并清除 X/Y 偏摆，一次手势仍然最多翻一个面。
- **验证**：`.tmp/probe-rot.html`（真实构建 + 真实指针事件）新增"**拖动中姿态 vs 松手停稳姿态**"的实测断言（弹回 ≤10°）、连续同方向翻面、俯仰翻过极点后背面朝前时的候选朝向（`+u` 屏幕右 / `+v` 屏幕下 / 不镜像），并复跑偏航、窄带自转与其归正、短滑弹回等回归项；`.tmp/probe-swipe.mjs` 的"俯仰限位"用例同步改写为"重复俯仰必须继续翻面"。

### 应该有

- 大面积、干净的高明度色块，第一眼先看到“好玩”和“可操作”。
- 软圆角、轻微鼓起的积木面、柔和接触阴影，让方块像亲手可触的玩具。
- 适度夸张的弹跳、亮度提升和星星/小方块庆祝元素，传达成功与奖励。
- 温和、积极的背景色和清楚的视觉层级；即使 Game Over 也保持友好，不制造压迫感。

### 不应该有

- 黑暗科幻、赛博朋克、写实金属、玻璃、水晶或军事机械感。
- 过度复杂的 3D 场景、厚重环境光遮蔽、深黑背景和高对比恐怖光影。
- 过多文字、复杂装饰、角色表情抢主体，或把玩法包装成战斗/破坏场景。
- 只靠发光和镜头震动表现爽感，导致棋盘、落点和消除关系无法辨认。

卡通感的优先级为：**轮廓与色块 > 圆润体积 > 轻量阴影 > 庆祝动效 > 装饰细节**。如果细节与可读性冲突，始终删除细节。

## 6. 方块与棋盘造型

### 6.1 方块

- 基础单位是规则立方体，边长在不同视角下保持一致的网格关系。
- 每个方块使用“主色面 + 一档较暗侧面 + 一档较亮顶面”的固定明暗关系，光源方向全局统一。
- 边缘使用轻微倒角或 1～2 像素的高光线，避免尖锐锯齿，也避免过度圆润的果冻效果。
- 相邻单位之间保留稳定缝隙，让形状轮廓可读；缝隙不能因动画或缩放忽大忽小。
- 禁止随机文字、复杂图案、仿金属反射、木纹、布纹和高频噪声材质。

### 6.2 3D 待填充空间

- 不使用独立的深蓝实体底板，也不使用包围整个 3D 区域的圆角玻璃容器；待填充空间直接显示在天蓝主背景上。
- 空间定位只保留底层半透明投影格面、当前活动层与落点辅助线；八角边线透明度降至极低、不再显示角标小方块，不绘制所有内部交叉线。
- 六面体(每面 5×5) 边界在默认视角下必须完整进入安全框；相机旋转到预设方向时也不得被顶部信息、候选槽或屏幕边缘裁切。
- 空间轮廓透明度分级：近侧关键边最清楚，远侧边弱化，内部非活动层仅在需要解释落点时出现。
- 已放置的高饱和彩色积木是空间的主要体积来源；积木逐渐增多后，辅助线应进一步淡出，避免线条覆盖方块。
- 背景可使用非常轻的云雾、中心泛光或软椭圆接触影帮助悬浮空间落位，但不能形成新的硬边底板。

### 6.3 镜头与安全框

- 透明交互容器继续覆盖整个 3D 操作区，用于接收拖拽和旋转输入，但不得绘制边框、卡片底色、内高光或硬阴影。
- 默认视角下，六面体(每面 5×5) 空间的全部关键角点都应进入画面；**六面体是主要操作区，允许贴到操作区边缘**（v0.2.25 起取景按"充满但不裁切"收口，左右窄带仅用于自转手势）。
- 中间 3D 区域拖动提供三个旋转自由度，但**一次手势只驱动一个轴**（v0.2.25 起）：水平滑动绕屏幕纵轴（Y）、在六面体水平范围内上下滑动绕屏幕横轴（X）、在六面体水平范围外上下滑动绕屏幕法线（Z，屏幕内自转）；**这三个轴固定在世界（屏幕）坐标，绝不跟随六面体旋转**（v0.2.27 起，此前欧拉分量累加会让转轴被另外两个角带走）；旋转方向跟手，旋转范围与速度应受控，避免空间方向跳变；Z 自转停稳后必须精确归正、不留歪斜。
- 移动端旋转到任何预设方向或调整世界 Y 轴视角后，空间投影不得进入顶部计分区或底部候选块区域；必要时动态后移相机，而不是裁切模型。
- 相机始终围绕 六面体(每面 5×5) 空间的几何中心旋转，不以底层或实体底座为旋转中心。
- 空间投影建议占 3D 操作区宽度的 66%～80%、高度的 78%～88%（PC 以高度为约束、移动端以宽度为约束）；优先完整显示，再追求视觉放大。
- 去掉底板后可添加低透明软椭圆影作为悬浮锚点，宽度不超过空间投影宽度的 65%，边缘必须完全羽化。

## 7. UI 视觉

- UI 采用紧凑、平面、圆角不超过 8px 的面板；避免把每个信息都包进悬浮卡片。
- 分数放在棋盘上方或侧上方，使用粗体数字和短促的变化动画。
- 当前 3 个方块放在棋盘下方或侧下方，预览底板尺寸固定，避免形状变化导致布局跳动。
- 右上角只保留一个齿轮设置按钮；声音、触感与重开收纳在设置面板中，主要确认动作使用图标加短文字。
- Game Over 只保留结果、分数和重开，不使用大段说明或营销文案。
- 字体优先使用系统无衬线字体，数字需有清楚的 `1`、`0`、`8` 区分；不使用未来感、手写体或夸张游戏字体。

## 8. 动效与反馈

- 放置：方块以 80～120ms 的短促回弹固定，落点产生轻微缩放或亮度确认。
- 非法位置：预览轻微左右抖动并显示红色轮廓，不使用持续闪烁。
- 线消除：先将完整线提亮 100～160ms，再以 160～240ms 收缩/淡出；保持格子位置可追踪。
- 多线消除：增加亮度、粒子数量和分数跳字尺寸，但粒子必须沿被消除的线运动，不能随机铺满屏幕。
- 候选线：使用低频呼吸高亮，周期约 1.2～1.8 秒；不使用快速闪烁、强烈镜头晃动或全屏白闪。
- 消除反馈降低白色过曝：以亮黄高亮、线色小方块与暖色星星营造积极奖励，泛光不得掩盖积木轮廓与落点预览。
- 粒子形状优先使用小立方体、短线和规则碎片，方向受线轴约束；禁止烟雾、火焰、液体和不可解释的魔法特效。

## 9. 减少 AI 感的制作约束

“减少 AI 感”不是降低细节，而是提高设计的一致性、可解释性和人工决策密度。所有新素材和效果遵守以下规则：

1. 先写清用途、尺寸、状态和明暗方向，再制作素材；不从模糊提示词直接生成最终资产。
2. 形状使用可复用的基础几何和明确比例；同类资产只允许少量有意设计的变体。
3. 光源、透视、边角半径、线宽和阴影软硬度全项目统一；发现同一物体多套光照时优先返工。
4. 不使用随机细节填充空白：随机划痕、随机高光、随机装饰、随机渐变、无意义字母和伪文字全部禁止。
5. 任何生成式素材只能作为草稿参考；运行时最终表现必须重建为可编辑的 HTML/CSS、Canvas、Shader 或 Three.js 参数化几何，并由美术人工检查轮廓、颜色与重复纹理。
6. UI 文案、图标和数值使用明确的设计稿，不让生成工具决定文字内容；禁止乱码和近似 Logo。
7. 每个新资产至少经过“缩小到实际游戏尺寸”和“灰度模式”检查：缩小后轮廓仍清楚，灰度后状态仍能区分。
8. 动效的持续时间、缓动、粒子数量和触发条件写入参数表；不以随机化掩盖反馈层级不足。

## 10. 程序化美术与渲染技术基线

### 10.1 运行时资产边界

- 游戏运行时的方块、棋盘、背景、UI、图标、材质、纹理、粒子、光影和过场全部由代码程序化生成。
- 禁止把外部 PNG/JPG/WebP/SVG、视频背景、预制粒子图集、GLTF/FBX/OBJ 模型或第三方素材包作为运行时视觉依赖。
- 允许使用 Three.js 参数化几何、HTML/CSS、Canvas 动态纹理、Shader、数字色板和运行时配置；即便使用 Canvas/Shader 生成纹理，也必须由代码确定并可复现。
- 宣传截图和视频可以基于真实运行画面做裁切、排版与字幕后期，但不得反向把宣传素材作为游戏运行时资源，也不得制作游戏内不可复现的效果。

### 10.2 高品质渲染组件

- Three.js 继续作为核心场景与几何渲染层，使用统一色彩空间、ACES tone mapping、圆角参数化积木、主光/环境补光/轮廓光和柔和阴影。
- 使用成熟开源组件 `postprocessing` 组织 RenderPass、SMAA 与 Bloom。Bloom 只作用于高亮材质和消除反馈，采用阈值控制，禁止全屏泛白。
- 使用成熟开源组件 `three.quarks` 管理批量粒子系统；粒子形态为程序化小立方体/规则碎片，沿 x/y/z 消除轴定向运动，不使用外部贴图图集。
- 渲染质量分为高性能档与低性能档：低性能档降低像素比、MSAA/SMAA 品质、Bloom 层级、阴影和粒子数量；两档必须保持相同的反馈语义与状态可读性。
- 所有粒子数量、寿命、速度、尺寸曲线、Bloom 阈值/强度、阴影尺寸与像素比上限集中管理，便于性能调优与验收复现。

## 11. 验收检查

- [ ] 1280×720 桌面截图中，棋盘在第一视觉层级，UI 不遮挡完整棋盘。
- [ ] 六面体(每面 5×5) 各层在默认视角可区分，旋转后没有颜色或阴影逻辑跳变。
- [ ] 合法、非法、已占用和遮挡状态不只依靠色相即可区分。
- [ ] 方块主色、顶面、侧面和阴影方向在所有形状中一致。
- [ ] 单线与多线消除反馈有明确强弱差异，但不遮挡下一次落点判断。
- [ ] 手机/窄窗口下分数、方块槽位和重开按钮不溢出、不互相覆盖。
- [ ] 截图中无乱码、随机伪文字、无意义纹理或不一致的光照。
- [ ] 美术参数能在代码或配置中集中调整，不把关键视觉值散落在组件内。
