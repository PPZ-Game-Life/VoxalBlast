## v0.8.1 侧带自转方向修复验收（2026-09-16）

用户报告：屏幕中间非六面体区域上下滑，右侧空白区符合预期，左侧与预期相反。

**原因**：竖滑的轴向划分只看手指落点是否在棋盘水平范围内（`isHorizontallyOnCube` → `screenBand`），出界即平面自转；但自转的符号左右两带共用 `ROTATE_STYLE.rollDirection` 一个值。自转是平面内旋转，"跟手"必须按手指所在的那条带定义：右侧带下滑时右边缘向下走（跟手，用户看到的"符合预期"），左侧带下滑时左边缘却向上走（相反）。也就是说两带里同向滑动必然得到方向相反的四分之一转，而代码只对其中一侧成立。

**修复**：`src/rendering/swipe.js` 新增 `bandRollSign()`（左带 -1、右带 +1），`swipeAngle()` 的自转项乘上带符号；`rollDirection` 仍是唯一方向旋钮（配置警告"不要再翻转方向值来追方向报告"依旧成立——这次不是翻旋钮，是补上缺失的带因子）。右侧带行为逐位不变。`main.js` 起手时采样 `screenBand()` 并随手势保存。

## v0.8.8 方位微调验收（2026-09-17）

制作人在 v0.8.7 上反馈："这一版，比上一版好。但是有一个问题，就是每次转完，都是到达同一个角度。" 诉求是：**允许玩家对正对屏幕的那一面微调角度，记住这个方位，翻面之后转到这个微调方位；微调区间主要是为了让主面多面对屏幕，超过太多就识别为翻面。**

**原因**：v0.8.6/v0.8.7 把停稳倾斜做成了一层**常量** `presentationYaw/Pitch`，并且在松手时把拖动余量全部丢弃（`planAxisStep` 只返回整面步进），所以无论玩家怎么拖，落点永远是同一个角度。

**改动**（`src/rendering/config.js`、`src/main.js`）：

- `cubePresentationWeight` / `presentationTilt` / 权重衰减（`presentationFadeAngle`、`presentationFadeOutEnd`、`presentationReturnStart`）整体删除——那套机制是为了把一层**固定**倾斜从旋转里挪开；方位变成玩家自己的之后，它必须**跟着手指可见**、并且**停在手指松开的位置**，不能淡出。`presentationYaw/Pitch` 改名为 `bearingYaw/bearingPitch`（出厂默认值，不再是常量）。
- 新增 `bearingYaw`/`bearingPitch` 运行时状态与 `planAxisRelease(axis, startBearing, angle)`：偏航/俯仰拖动**直接移动方位**（不是在外面叠一层旋转），因此松手时"画面上的姿态 = 被保留的姿态"，微调路径**零动画、零回弹**；越出 `±stepThreshold` 则翻一个面并把方位还原成玩家之前调好的值。平面自转永远不参与方位。
- 探针：`rotation()` 增加 `bearing`/`bearingDeg`；`npm run probe:framing` 新增 bearing 段（四条断言）；删除已失效的"偏摆淡出"断言。`__voxalblast.faces().uprightDeg` 改在**方位**上度量——在渲染姿态上度量会把合法倒置面读成 180°、把自转到位的面读成 90°。
- 存档随 `base` 一起保存方位，读档按 ±阈值夹一次；重新开始复位。

**结果**：

- [x] `npm run probe:framing` bearing 段四条全过：阈值内的 −11.92° 拖动**被原样保留**（实测 −11.92°、`base` 未变）；翻面后**方位保持 −16.92° 不变而 `base` 已变**；从 −16.92° 再拖 21.8°（总偏移必然越出 ±30°）**翻面且方位仍是 −16.92°**；侧带阈值内自转**不留任何残角**。
- [x] 停稳构图（出厂方位）不变：主面 71.4%、右面 18.1%、顶面 10.5%，24 朝向零离散；`uprightDeg` 0.00°。
- [x] 拖动全程轴漂移 0°（偏航 / 俯仰 / 平面自转），轴偏斜 0° / 5.98° / 11.84°（3/4 视角固有），阈值不变。
- [x] `npm run probe:swipe` 三项全 OK、`npm test` 244/244、`npm run build` 通过、`npm run shot` 四项无 console/GL 错误（`artifacts/visual/v0.8.8-*.png`）。
- [x] 可用区间已实测并记录（见 03 §2.1）：偏航 −25° → 主面 46.4%，−5° → 71.4%，+25° → 89.0% 且顶面 0.0%。**往正视方向调过头会退化成平面网格**，属玩家自主选择；默认值刻意留在 71.4%。

## v0.8.6 → v0.8.7 停稳构图与旋转观感验收（2026-09-17）

制作人报告两个问题：停稳后正对玩家的主面面积不足、侧面顶面露得太多；旋转过程发歪，"像带着停稳时的斜角一起旋转"。建议稿是 `docs/Temporary/Cube-Rotation-Interaction-Optimization.md`（临时交接稿，目录已 gitignore，不入库）。**本轮经过一次否决与返工，两版记录都留在这里。**

**根因：两个问题同一个源——相机停在 3/4 视角** `[0.52, 0.48, 1.05]`（26.4° 偏航 / 22.3° 俯仰）。

- 停稳时三个可见面几乎平分轮廓（约 65% / 19% / 16%，正交口径 52% / 25% / 23%），主面不构成视觉主体。
- 世界 X 轴在该俯仰下投影成偏离水平 **10.63°** 的屏幕线，世界 Z 轴偏 **37.43°**——"发歪"来自相机，姿态层修不掉（世界 Y 轴恰好仍投成竖直，所以只有偏航看着是正的）。
- 第二重来源：旧的 `restOffsetYaw/Pitch`（各 ≤8°）存的是上一次手势的溢出量，且被冻结在实时旋转**外面**；只要它非零，主体就一直绕着一根斜轴转，而且每次停稳的斜角都不一样。

### v0.8.6（已否决）

把整个 3/4 视角搬进六面体：`cameraDirection` 改正视 `[0, 0, 1]`，由 17.5°/15.5° 的双轴**展示偏摆**提供立体感，主面推到 **82.8%** 以贴合建议稿的 82–88%。

- 正面接近正视角时，每一格都是**近正方形**，读起来就是一张平面网格；v0.8.5 的立体感本来就来自侧面/顶面占了 40% 的轮廓。
- 双轴偏摆把棋盘在画面上压歪 **−4.77°**（`Ry·Rx` 复合：最后施加的轴看着正，另一个轴带着整块棋盘歪）。网格姿态本身永远不歪，歪的是姿态呈现层。

- `BOARD_STYLE.cameraDirection` = `[0.34, 0.33, 1.0]`（约 18.8°/17.6°）：3/4 视角回到**相机**，六面体竖直棱恒为铅直。
