# VoxalBlast 美术效果优化流程规范

> **流程基线：v0.8.4 / 2026-09-17**  
> 规则基线：v0.8.4 加权候选池；视觉基线：v0.8.0「木质田园」。  
> 适用范围：VoxalBlast 的视觉重做、阶段性美术升级与参考图还原。  
> 本文规定“如何改、按什么顺序改、用什么证据验收”，不替代 [美术方向与视觉规范](../Planning/05-美术方向与视觉规范.md) 中的现行风格与参数裁决。

## 0. 目标与优先级

VoxalBlast 已是可玩的 Three.js 益智游戏。本流程以任务开始时确认的规则、交互、计分、存档和平台行为为**冻结基线**；美术优化的任务是：

> **在不改变玩法行为的前提下，把程序员原型感持续替换为统一、温暖、可触摸、可商业发布的休闲游戏视觉。**

每轮优化按以下优先级裁决：

1. 玩法、交互、信息可读性和存档行为不回归；
2. 与本轮目标参考图和已批准美术方向保持视觉一致；
3. Web / CrazyGames 运行性能；
4. 可维护性与视觉参数可控性；
5. 资源体积。

“像参考图”只约束视觉呈现，不能凌驾于第 1 条和性能底线之上。如果并行玩法开发改变了规则基线，应先同步 02 与本任务基线、重新截图，再继续视觉轮，不能拿新旧玩法状态直接比图。

## 2. 不可破坏的硬边界

### 2.1 不改玩法

纯美术任务默认禁止改动：

- 棋盘与 98 个唯一外壳格的拓扑；
- 放置、合法性、六面结算和共享棱角规则；
- 得分、连击、荣誉和反馈等级判定；
- 候选生成、批次与道具配额；
- 鼠标、触摸、键盘、旋转方向和吸附行为；
- 单局流程、存档结构和纪录；
- CrazyGames SDK 与暂停/恢复流程。

确有必要时，必须拆成独立功能任务，不得混在“调美术”提交中。

每轮开始和交付前都执行 `git diff --name-only` 核对变更面：纯视觉轮原则上不得包含 `src/game/**`、`src/platform/**`；`src/main.js` 只能修改表现相关段。若出现例外，必须在任务单中逐文件说明原因，并按功能改动执行完整规则回归。

### 2.2 逻辑驱动表现

推荐数据流：

```text
Game Logic / Session State
          ↓
Presentation State（只读映射）
          ↓
Three.js Renderer / DOM UI / FX
```

- 渲染层读取状态，不在材质、动画或 DOM 回调里重新实现玩法规则。
- “是否可放”“消了几条线”“反馈等级是多少”由现有逻辑给出；表现层只决定颜色、时序、强度和动画。
- 不为方便做动画而复制一套棋盘状态。
- 不让截图资产承载动态分数、连击、数量或规则信息。

### 2.3 一轮只解决一个主要视觉问题

每次迭代必须先写一句可验证假设，例如：

> “当前方块塑料感过强，原因是清漆高光窄而亮；本轮只调整粗糙度、清漆和主光面积，不改色板与相机。”

同一轮最多处理 1 个主要问题、1～3 组强相关参数。禁止同时随意改相机、材质、色板、背景和 UI，再凭感觉挑一个结果。§7 的 Phase 是由多轮迭代组成的阶段，不代表要在一次提交里同时改完该 Phase 列出的全部项目。

## 3. 目标视觉语言

总体关键词：

- 休闲益智；
- 温暖、明亮、友好；
- 软化的风格化 3D；
- 木质田园与奶油纸 UI；
- 圆润、厚实、玩具感；
- 轻微手绘质感；
- 高可读性和克制的奖励反馈。

禁止走向：

- 写实、金属、玻璃、水晶、科幻、霓虹；
- 默认 WebGL、默认 HTML 控件或技术仪表盘；
- 过度极简、薄线图标、冷灰企业 UI；
- 低多边形拼凑感；
- 高频摄影木纹、重划痕、脏污或随机噪声；
- 为“高级感”压暗画面、降低主方块可读性。

缩到约 240px 宽时，第一眼应先读到“明亮、可玩的彩色积木游戏”，其次才是田园和木质装饰。

## 4. 屏幕四层架构

### Layer A — 2D 背景

职责：天空、云、远山、村庄、河流、草坡、花草和前景植物。

当前入口：

- `public/art/pastoral-valley.webp`：已发布的主背景；
- `src/rendering/pastoralBackdrop.js`：加载、SVG 兜底和层级；
- `public/art/README.md`：来源、尺寸和制作说明。

规则：

- 不用大量 Three.js 几何重建整片田园；
- 背景永远次于棋盘，远景低对比、低细节；
- 背景层不接收指针事件，不影响可访问性和手势；
- 可增加远/中/前景分层与轻微视差，但默认关闭大幅运动；
- 手机裁切必须保留连续天空、地平线和草地，关键景物不得只在桌面角落成立；
- 当前 `npm run shot` 硬断言 `.pastoral-backdrop` 同时保留 SVG 兜底与已加载的 `<img>`，且覆盖整个视口。若背景改成 CSS image、懒加载或多层 DOM，必须同轮同步 `tools/screenshot.mjs` 的探针与 04 §4，不能删掉断言来“通过”。

### Layer B — 主 3D 游戏

职责：中心六面体、原木格、彩漆格、候选/拖拽同源方块、落点预览、旋转、阴影和 3D 粒子。

当前入口：

- `src/main.js`；
- `src/rendering/config.js`；
- `src/rendering/woodTexture.js`；
- `src/rendering/toyLights.js`；
- `src/rendering/threeCompat.js`。

规则：

- 继续使用 98 个唯一晶格实体，不退回六面重复建模；
- 棋盘、候选和拖拽继续共享圆角几何与材质系统；
- 放置只改变材质/状态，不随机改变方块尺寸、位置或高度；
- 相机错位不能靠逐块缩放补偿；
- 真实读深度的后处理接入前，先复核 `threeCompat.js` 的深度纹理兼容边界。

### Layer C — DOM UI

职责：SCORE / BEST / CHAIN、设置与操作入口、候选托盘、道具、数量徽标、主页、弹窗和结算。

当前入口：

- `index.html`；
- `src/styles.css`：历史布局与断点；
- `src/toy.css`：现行视觉覆盖；
- `src/ui/icons.js`：代码生成 SVG 图标。

规则：

- 动态数字和文案必须保持真实 DOM 文本；
- UI 世界尺寸与 Three.js 世界尺寸分离，响应式用布局和组件尺寸解决；
- 视觉覆盖不得重新声明无关的 `width/height/gap/order`，避免静默破坏手机布局；
- 新规则放在现行覆盖层，并明确受哪些断点控制；
- 不截整块动态面板当图片，也不把所有质感强行用通用 CSS 渐变模拟。

### Layer D — FX

职责：分数跳字、连击、荣誉横幅、亮度脉冲、消除光束、粒子、音效和触感配合。

规则：

- 反馈顺序为“确认 → 消除 → 得分”，不提前庆祝；
- 强度由现有反馈等级驱动；
- 粒子使用小立方体、短线、星形或规则碎片，避免烟、火、液体和魔法雾；
- 最高级反馈也不能遮挡棋盘或阻塞输入；
- `prefers-reduced-motion` 下保留结果信息，减少位移、摇动和持续动画。

## 5. 关键对象的质量门槛

### 5.1 单个方块

单个方块是所有视觉升级的第一道门。

必须具备：

- 真实圆角和可受光的物理倒角；
- 平整主体面，不能读成鼓包软垫；
- 顶面、受光侧和背光侧关系稳定；
- 宽、软、低强度高光；
- 轻微且确定性的表面变化；
- 缩小到真实游戏尺寸后轮廓仍清楚。

禁止：

- 以普通 `BoxGeometry` 作为最终方块；
- 只靠贴图假装所有倒角；
- 高频程序噪声、摄影木纹、重划痕；
- 强塑料镜面、霓虹外发光；
- 同类方块随机改变圆角、光向或比例。

当前 `RoundedBoxGeometry` 和统一几何机制应视为可继承基础；具体尺寸与材质值只在 05 和 `config.js` 维护，本文不复制第二份易漂移参数。

### 5.2 原木与彩漆

- 原木：暖、奶油、低对比、轻木纤维、半哑光；
- 彩漆色值与形状映射只以 05 §3 和 `src/game/shapes.js` 为准，本文不建立第二份色板；
- 单屏实际出现的主色控制在 4～5 类，避免霓虹；
- 彩漆与原木必须共享造型与光照，但材质层次可区分；
- 灰度下仍能区分背板、原木格和彩漆格。

### 5.3 棋盘、间隙与相机

- 格间保留细缝，使每格独立可读但仍组成一个完整大六面体；
- 当前操作面提示轻量，不把其他面压成不可见；
- 相机对比必须同时看 FOV、距离、仰角、可见面比例、屏占比和中心位置；
- 不允许通过随机改变块尺寸弥补构图问题；
- 八角、共享棱边、斜视缝隙和旋转中间帧均需单独检查；
- **相机不是纯视觉旋钮**：拖拽转角标尺来自六面体屏幕投影。凡修改 FOV、距离、目标点或屏占比，必须记录同视口同姿态下“翻一面所需拖动像素 / 六面体投影宽度”的前后值，重跑 `npm run probe:swipe`，并人工复测 390×844 与 844×390 的短滑弹回、过阈值翻面和侧带定轴。手感漂移即视为交互回归。

  已记录实例（v0.8.6/v0.8.7，1280×900，FOV 30 与取景系数未动，测法为 `git stash push -- src` 前后各跑一次）：

  | 量 | v0.8.5 | v0.8.7 | 变化 |
  | --- | ---: | ---: | ---: |
  | 六面体屏幕包围盒 | 454 × 464.9px | 458.5 × 456.1px | 宽 +1.0%、高 −1.9% |
  | 翻一面所需拖动（偏航） | 227px | 229.3px | +1.0% |
  | 翻一面所需拖动（俯仰） | 232.4px | 228.1px | −1.9% |
  | 判定阈值对应拖动（偏航 / 俯仰） | 75.1 / 77.0px | 75.9 / 75.5px | +1.1% / −1.9% |
  | 世界 Y / X / Z 轴在屏幕上的方向偏斜 | −90°（正竖直）/ −10.63° / 37.43° | −90° / −5.98° / 38.89°（自转轴 `alongView` 0.90） | 俯仰轴减半，抗自转仍偏 |

  v0.8.6 一度把相机改成正视 `[0,0,1]`（三者全部归零），但停稳构图退化成平面网格且棋盘被压歪，已被制作人否决；v0.8.7 把 3/4 视角放回相机。**注意"轴偏斜归零"与"停稳是立体六面体"不可兼得**：轴偏斜来自相机俯仰，而立体感来自相机俯仰，两者是同一个旋钮。阈值 `stepThreshold` 保持 0.52 rad（≈30°），标尺规则（半屏投影 = 一面）未变。

  **v0.8.26 补：这套取舍作用在"停靠"上时结论要改口径。** 制作人要求停靠**正对镜头**（理由：静止时左右两侧面的可见面积必须一致），于是动的是 `ROTATE_STYLE.bearingYaw`（0° → +16°，即相机自身偏航），**相机没动**：3/4 读感从"停靠自带"改成"微调拨出来"（区间两端各露 10.9% 侧面，一左一右互为镜像）。副作用是好的——正对时正面与屏幕轴逐轴对齐，v0.8.6 以来那族"网格在屏幕面内旋转"的数字直接归零：24 朝向面内滚转离散 2.27° → **0.00°**，正面网格线屏幕斜切 −0.34…2.95° → **−0.29…0.29°**。所以"不可兼得"只在那次"把**相机**推成正视"的语境里成立：停靠正对 + 保留相机俯仰 8° 的檐，两个目标不冲突。

  **相机不是纯视觉旋钮，还有第二层含义（v0.8.7 补）**：停稳时棋盘是否"歪"也只由相机与方位倾斜的施加顺序决定——相机 up = +Y 时网格姿态恒铅直；一旦把俯仰以"偏航在后"的顺序复合进方位，棋盘会被压歪（v0.8.6 实测 −4.77°）。现行顺序是 `Rx(pitch) · Ry(yaw)`，对**任何**玩家可调方位都保持铅直。改这块必须同时跑 `npm run probe:framing` 的 `uprightDeg`（≤0.5°）与 `minOtherShare`（≥6%）。

  **第三层含义（v0.8.8/v0.8.9 补，v0.8.24–26 定稿）**：停稳构图依赖**运行时状态**（玩家调好的方位），不再是常量。`npm run probe:framing` 的 framing 段只在**出厂方位**下测量（探针用全新 profile、无存档），所以它仍然可比；玩家拨到区间端点时主面占比会显著偏移，`bearingMargin`（v0.8.24 起是以出厂停靠角度为中心的对称 ±10° 偏航 / ±3° 俯仰；v0.8.26 起出厂停靠 = **正对镜头**，偏航 +16°）就是为此存在的边界。凡改动相机、`stepThreshold`、出厂 `bearingYaw/Pitch`、`bearingMargin` 或 `bearingResistance`，framing 段与 bearing 段必须一起重跑。**另注意探针自身的标尺**：拖动→角度的标尺是六面体**当次**的屏幕轮廓，而轮廓随方位变化——同一视口、同一台相机下，出厂（正对）是 **378.9px**，而 3/4 停靠（相对偏航 16°）是 **452.7px**，差 19%；所以探针里凡把"度"换算成 px 的拖动都要先重取一次 `bounds()`（bearing 段的 `measureRuler()`），否则会把标尺误差误判成应用侧映射有偏。

  **构图与视口无关，但必须证明**：`refreshCameraProjection()` 由画布宽高比解相机距离，所以构图原则上随视口变化。v0.8.9 加了 `npm run probe:framing --viewport=WxH`，并在七个手机与桌面视口复测过（主面 66.1–69.0%、非主面 11.9–20.3%、竖直 0.00°）。**只在 1280×900 跑一次不足以证明手机正常**——真机截图与桌面测数不一致时，先跑这一项。

  **不要用 shell 回写含中文的源码**：v0.8.8 的 `src/rendering/config.js` 中文注释被 `Get-Content -Raw` + `Set-Content -Encoding utf8` 在 GBK 控制台编码下整段写成乱码（42 处），并随提交推送到远端，v0.8.9 才从干净提交取回重做。要批量改源码就用编辑器工具；要批量跑参数扫描就改**探针**（加 `--viewport=` 这类开关），不要一边改源码一边 `Set-Content` 回写。

### 5.4 方块状态

| 状态 | 要求 |
| --- | --- |
| Normal | 标准材质，不带额外发光 |
| Hover | 轻微提亮或接触反馈，不改变尺寸判定 |
| Selected | 沿用 05 / 03 的现行选中语义，以描边、明度或接触阴影区分；禁用独立发光图层 |
| Ghost | 半透明、边缘清楚，与手中幽灵互斥 |
| Valid | 使用 05 §3 的有效色，允许轻脉冲；仍可看清目标格 |
| Invalid | 使用 05 §3 的无效色作轻提示，不把整盘变成警报画面 |
| Clearing | 先短暂确认，再按轴消除；效果不得埋入壳体 |

### 5.5 UI

组件拆分而不是整图裁切。下列名称是**设计概念名**，不是代码组件；本项目仍使用原生 DOM/CSS：

- `ScorePanel` → `.score-chip` / `.best-chip` / `.chain-chip`：木/纸底、标签和动态数值；
- `SquareButton` → `.icon-button` / `.modal-close`：共享木质底，图标独立；
- `PieceTray` → `.bottom-panel` / `.piece-slot`：共享框架、三个槽位和独立 3D 候选；
- `PowerUpButton` → `.item-button`：共享圆形按钮、独立图标和动态数量徽标；
- 弹窗 → `.modal-content`：共享框架、标题、正文和按钮状态。

UI 视觉要求：

- 奶油纸中心、暖木框、圆润、轻微不规则、柔和投影；
- 按钮有抬起/按下位移和明确焦点态；
- 图标使用粗线、可读、略有手绘感的统一体系；颜色必须按实际底色做对比度验收。当前代码是深棕系，而 05 §6 留有奶油白旧裁决；在 05/03 完成统一前，不得仅凭本文翻转图标颜色；
- 重要数字最大，标签次之，装饰最后；
- 禁止细线现代图标、系统默认按钮和不可编辑伪文字。

### 5.6 背景与特效

- 远景降对比，必要时轻微模糊和空气透视；
- 棋盘附近不得出现比彩色积木更亮、更饱和的大色块；
- 分数跳字使用浅色字、深轮廓、短促上移；
- 连击可有缩放和小型爆发，但不常驻抢焦点；
- 消除推荐节奏：高亮 → 轻缩放/脉冲 → 规则碎片 → 消失 → 分数反馈。

## 6. 资产策略与反 AI 约束

### 6.1 选择实现方式

每个对象按以下顺序判断：

1. **实时交互或频繁变化？** 优先 Three.js / DOM；
2. **只是静态布景？** 优先 WebP 等 2D 资产；
3. **需动态文字或数量？** 背板可用图片，内容必须是 DOM；
4. **CSS 已能稳定复现？** 保留 CSS，不为“有资产”而增加图片；
5. **CSS 难以形成手绘木框或不规则边缘？** 使用可复用九宫格/切片资产，不截整张动态面板。

建议的新资产按职责放入 `public/art/` 的 `background/`、`ui/`、`textures/`、`fx/` 子目录。现有 `pastoral-valley.webp` 暂不因目录规范被无意义搬迁。

### 6.2 资源要求

- 图片优先 WebP；透明边缘确有需要时使用 PNG/WebP alpha；
- 同类组件复用底图、几何、材质和图标，不创建大量近似副本；
- 新资源必须记录用途、尺寸、裁切方式、来源、许可、压缩结果和失败兜底；
- 纹理在目标显示尺寸和 2×像素密度下验证，不盲目上超大图；
- 任何新增资源都记录构建前后体积差。

### 6.3 减少 AI 生成感

- 生成式图片只能提供草稿或静态布景底稿，最终资源需人工校正构图、边缘、透视、光向和重复纹理；
- UI 文案、数字、Logo、图标和状态不得交给生成图决定；
- 禁止随机划痕、随机装饰、随机高光、乱码和无意义符号；
- 同类资产只保留少量有意变体；
- 新资产必须通过实际尺寸、240px 缩略图和灰度三项检查；
- 所有运行时随机纹理必须有固定种子，同一版本重复截图结果一致。

## 7. 标准实施阶段

每次完整视觉重做必须按以下顺序推进。已有成熟部分可以“核验后跳过”，但不能无证据跳过。

### Phase 0 — 建立任务基线

开始条件：目标图、范围和责任边界可读。

产出：

- 本轮目标一句话；
- 规则 / 交互 / 视觉 / `package.json` 版本基线；
- 参考图本地路径或可访问 URL；
- 参考截图对应的游戏状态；
- 当前基线截图；
- 禁改模块清单；
- 本轮允许修改的文件，并保存开始时的 `git diff --name-only`；
- 最大三个视觉差异；
- 性能、视口和资源体积基线。

如果目标图不可访问，流程停在 Phase 0，不得猜图实现。

### Phase 1 — 单个方块

目标：只把**一个方块**的几何、倒角、材质、粗糙度和受光做到可接受。

验收：

- 放大图能看到真实倒角受光；
- 实际尺寸不糊成圆点或塑料糖果；
- 原木和彩漆共享造型但材质可辨；
- 候选预览与棋盘视觉一致；
- 材质与几何为可复用系统，而非单块特例。

未通过，不进入 Phase 2。

### Phase 2 — 完整六面体

目标：解决格间距、整体比例、相机、颜色关系、木格、阴影和共享棱角。

验收：

- 98 个实体与 150 个表面映射不变；
- 棱角无重复、闪烁、挂块或透光；
- 相机屏占比接近目标；
- 当前面、相邻面和背光面层次清楚；
- 放置只换表现状态，不改变规则坐标；
- 旋转中间帧仍读作完整玩具立方体。

### Phase 3 — 主要 UI

按组件完成：顶部信息 → 主按钮 → 候选托盘 → 道具 → 弹窗/结算。

验收：

- 动态内容仍是 HTML/text；
- 组件有 normal / hover / focus / pressed / disabled 状态；
- 1280×720、手机竖屏和短横屏均可达；
- 候选拖拽源与取消区没有被装饰层截获；
- UI 与棋盘共享木质/奶油纸语言，但不抢主焦点。

### Phase 4 — 背景

目标：建立晴朗田园、暖日光和空间层次。

验收：

- 桌面、竖屏、横屏裁切成立；
- WebP 失败时兜底仍可见；通过 CDP 阻断 `pastoral-valley.webp` 请求，或在隔离的正式构建副本中临时改名来验证，不在工作树中删除正式资产；
- `pointer-events: none`；
- 背景不抬高饱和度与棋盘竞争；
- 若有视差，低性能档与 reduced-motion 可关闭。

### Phase 5 — FX

目标：让成功反馈清楚、短促、有层级。

验收：

- 反馈等级强弱可辨；
- 不遮挡下一步判断；
- 不改变逻辑结算时机；
- 粒子异常不导致动画循环停摆；
- reduced-motion 下仍能读到结果。

### Phase 6 — 最终比对与回归

目标：证明视觉变好，且玩法、交互、性能和构建没有回归。

产出：

- 同状态、同视口、同裁切的目标/改前/改后图；
- 差异列表及未解决项；
- 规则测试、构建、截图和人工回归结果；
- 新增资源与包体差异；
- 按改动同步 02 / 03 / 04 / 05 / ARCHITECTURE，并检查本地文档链接；
- 发布级改动同步 `package.json` 版本；不属于发布级改动时明确写“不升版”及理由；
- 交付前再次用 `git diff --name-only` 核对禁改范围；
- 在任务授权包含版本控制时完成提交与推送并记录 commit/远端；未授权时只报告待提交状态，不擅自推送；
- 美术负责人结论：通过 / 附条件通过 / 退回。

## 9. 性能与响应式门槛

### 9.1 性能

优先：

- 共享几何和材质；
- 纹理复用；
- 批量粒子或实例化；
- WebP 与合理像素尺寸；
- 低性能档降低阴影、像素比、后处理和粒子；
- 静态背景放在 DOM，不占主 3D 场景 draw call。

避免：

- 大量独立材质；
- 透明网格叠层；
- 无收益的全屏后处理；
- 每格独立高分辨率纹理；
- 为 UI 装饰增加常驻动画循环；
- 用超大贴图弥补相机和布局问题。

每轮至少记录：构建体积变化、控制台/GL 错误、桌面与物理手机的主观流畅度；有条件时记录平均 FPS、1% low、峰值内存和加载耗时。未测物理手机时必须明确写“未验证”，不能用本机构建成功替代。

### 9.2 响应式

- 六面体始终是主焦点；
- DOM UI 独立缩放和重排，不通过改整个 Three.js 世界尺寸解决；
- 手机候选保持在拇指可达区；
- 安全区、短屏和横屏按 03 的现行断点回归；
- 所有装饰层不得扩大命中区或阻断拖放；
- 文案增长、分数位数增长和本地化后仍不溢出。

## 11. Definition of Done

一次视觉优化只有同时满足以下条件才算完成：

- 玩法和交互行为保持不变；
- 中心六面体在构图、相机和块面质感上接近批准参考；
- 单块圆润、有触感、有稳定倒角受光，不像默认 WebGL 方盒；
- 光照明亮、柔和、温暖，不过曝、不塑料；
- UI 使用可复用组件和资产，动态数据仍真实可用；
- 背景符合木质田园方向且视觉退后；
- 状态、消除和奖励反馈层级明确；
- 桌面、手机竖屏和短横屏均可操作；
- 自动检查和必要人工回归通过；
- 对比截图能明确证明“最大差异已缩小”；
- 受影响文档、版本及版本控制交付状态已同步记录；
- 未完成项、性能边界和资源来源已记录。

最终观感应是**已商业发布的休闲益智游戏**，而不是给程序功能套上一层装饰。
