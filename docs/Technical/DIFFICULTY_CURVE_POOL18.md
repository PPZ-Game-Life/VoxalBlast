## 0. 结论先行（赶时间看这段）

1. **三件已按制作人裁决落码**：`Cross 5` / `U 5` / `T 5` 各权重 **1**，总权重 20.4 → **23.4**；
   颜色按 v0.8.17 木色带规则**在渲染空间**扫出（`#d62fd6` / `#2fd64b` / `#d13c2e`），
   与 4 格 `T` 的 ΔE = 36.4，实机截图确认不像木色（§3）。
2. **难度确实涨了，但幅度取决于口径，而"玩家实际遇到"的那一档比盲臂大一倍**：
   - **盲臂（池子本身）**：`random` 中位 **32 → 29**（−9%）、受限均步 **40.6 → 34.7**（−14.5%），
     配对检验 p = 0.0002；`clear` 结束率 **56.7% → 65.2%**（+8.5pp，Wilson 区间不重叠）。
   - **真实发牌器（玩家实际遇到）**：`random` 中位 **26 → 20**（−23%）、受限均步 −10.6%，
     配对 Δ均步 CI 不含 0（p = 0.0031）；`noise` 中位 **92 → 77**（−16.3%）、受限均步 −14.6%。
   - 交接单 §3.2 粗估 `random` 中位掉 25%~40% ⇒ **真实发牌器侧（−23%）落在估计区间下沿附近，
     盲臂侧（−9%）明显低于估计**。不能用盲臂数字去替代玩家体验（原因见 §8.3）。
3. **在"典型玩家"代理 `noise` 上，池子效应统计不可见**：中位 170 → 167（bootstrap CI −18.0 ~ +15.0 含 0，
   符号检验 p = 0.49）、受限均步 −3.3%。`lookahead`（会规划的玩家）**完全不受影响甚至略好**
   （受限均步 +0.5%）。**含义：这次改动惩罚的是"乱放/只顾清线"的打法，不是"会留空间"的打法**——
   正是交接单 §3.4 要的技术梯度。
4. ⚠️ **`Cross 5` 是唯一的压力源，而且它命中了交接单 §3.5 的"必须单独裁决"条款**：
   零落点占比 **13.09%**（`L 5` 的 7.6 倍）、**平均合法落点 5.37**（判读线：低于 10 必须单独裁决 → 命中；
   `Block 9` 是 3.19，`L 5` 是 22.84）、死亡手牌含它 **26.33%**（判读线 30%，未触发，但只差 3.7pp）。
   `U 5` / `T 5` 全部落在安全侧（零落点 2.16% / 2.61%，平均落点 26.79 / 20.53）。
5. ⚠️ **反直觉发现：三件齐上比只加十字更温和。** G→J（只加十字）`random` 受限均步 **−8.4**、
   `noise` **−24.6**；G→K（三件齐上）`random` **−6.0**、`noise` **−20.7**。原因是 `U 5` / `T 5` 是"能补线"
   的宽容件，同时把四格件的份额从 58.8% 稀释到 51.3%。**含义：若日后要回退，第一个该动的是十字，
   而且不该"三件一起降"**（交接单 §5 的旋钮顺序是对的，这里给出它成立的原因）。
6. ⚠️ **交接单 §5 第 2/3 步的两条 `staged` 命令不是"弱"，是"无效"**：
   `pool18/staged` 与 `pool15/staged` **每一个指标差 0.00**，五个新形状的实收槽位全部为 **0**。
   `staged` 不是"现行盘面感知发牌"，而是 `difficulty-model.mjs` 自带的分阶段发牌，
   且它的 `GROUPS` 只包含最初的 10 个形状 —— 池子里所有四格以上的件（`Rect 6` / `L 5` / `Slant 3` /
   `Line 4` / `Block 9` / 三个五格件）在 `staged` 口径下**一次都不会被发出**。
   "玩家实际会遇到什么"只能看 §8 的真实发牌器。
7. ⚠️ **通过线 ② 在任何口径下都不由基线满足，属口径问题，见 §9**：
   `random` 的 `stepsAll.p50` 在三个口径下分别是 **77（staged）/ 35（uniform）/ 23（真实发牌器）**，
   全部 < 40；`random` 的 `endedPct` 三者都是 **100%** > 99%。**基线自己就不在线内**，
   所以这一条不能当"本次回退与否"的判据。
8. ⚠️ **通过线 ③ 的 `space` 打法在本口径下不可测**（两个池都是 **0.0% 结束率、受限均步 = 600 上限**，
   天花板效应，指标没有分辨率）。改用 `lookahead`（真实发牌器下"考虑剩余手牌与空间"的打法）
   与 `noise` 作为替代读数，③ 的**意图**成立，见 §7。
9. **颜色扫描必须用渲染空间，这是本次顺带查出的口径修正**：`src/rendering/referencePalette.js`
   把 14 个 v0.9.0 之前的逻辑色映射成"漆色"，其余**原样直通** —— 所以玩家看到的 `Dot` 是 `#ff1644`、
   `Block 9` 是 `#9500f5`，而 `Line 4` 和本次三个新件看到的就是写在 `shapes.js` 里的值。
   按渲染空间重扫后，三个新件的判据全部通过，且它们引入的最紧一对（22.8）仍比池子里**已有的**
   七对更松。**同时查出两个既有问题（不是本次引入）**：渲染后的 `Line 3`（`#ffc400`）落在木色带内；
   渲染后的调色板里有 5 对 ΔE < 20（最紧 `Square`/`Block 9` = **5.1**、`L`/`S` = **6.5**）。见 §3.3。
10. ⚠️ **真实发牌器把三个新件"主动拉回来"了两倍，这是本轮最重要的操作性发现**：
    基础占比三件合计 12.82%，实收 **25.68%（2.00×）**，其中 `U 5` **2.79×**、`Cross 5` **2.14×**
    （`Block 9` 当年只有 1.58×）。含义：**"降权重"这个旋钮的实际效力会被打折，只有冷却能真正削住峰值**——
    交接单 §6 把 S1/S2 定为备用旋钮的判断是对的，这里给出量级。见 §8.3。
11. **发牌器健康度（④）通过，而且方向与预测相反**：`fallback` 率**下降**（`D/random` 6.63% → 4.91%、
    `D/noise` 55.41% → 51.07%；`deal-perf` 四档 fallback 158→158 / 90→87 / 57→36 / 71→46），
    `UNKNOWN` 与 `refused` 全程 **0** ⇒ 交接单 §3.3 预测的"发牌器先被顶住"**没有发生**，
    §4.2 S3 的预算重标定**不需要做**。
12. **性能（⑤）通过，但 50ms 那条子线被推过了**：最坏 p95 **51.9 → 60.4ms**（+16.4%，预算 150ms 以内）；
    但 §11.2 的"无 >50ms 主线程长任务"在改动前就已擦线（`session.deal()` p95 = 50.1ms），
    改动后 p50 就是 46.8ms、p95 58.1ms ⇒ **多数发牌现在跨过 50ms**。需裁决（§8.1）。

### 1.1 冻结基线（这一步是关键，别跳过）

`deal-experiments.mjs` 的 `SHIPPED_WEIGHTS` 原来是 `{ ...SHAPE_WEIGHTS }`（**展开**），
它只是"当时的副本"——加完三件之后，展开会让 **A/B/E/F 四个已发布的臂一起变成 18 类**，
等于把六个已发布臂静默改写，而不是新增臂。本轮把它改成**按名字字面冻结**的 `POOL15_WEIGHTS`，
并新增 `POOL15_SHAPES`（按名字解析，不切片 `SHAPES`）。A/B/E/F 因此**逐位复现**：

```
E/random（本次运行）: endedPct 100, p50 34, KM 中位 34
E/random（已发布 v0.9.0-p1.0 summary）: endedPct 100, p50 34, KM 中位 34   ← 完全相同
```

这也是**"台架是确定性的、因此与已发布 summary 做前后对照是有效的"**这一说法的直接证据。

**唯一跟随 `SHAPE_WEIGHTS` 的仍然是 `ship` 池**（`difficulty-model.mjs`）与
**盘面感知臂 C/D**（它们的候选表由 `src/game/dealer.js` 的 `weightedTable()` 从
`SHAPE_WEIGHTS` 现建，**没有注入缝**，唯一的既有杠杆是 Block 9 冷却——见 `armCForceBlock9Out`）。
所以盘面感知的 15 类基线**不可能**在同一次运行里冻结，前后对照只能跨运行做（§8），
臂的设计行新增 `followsGame` 字段把这件事写在报告里。

## 2. 三个口径的区别（读本文前必须分清）

| 口径 | 命令 | 它回答什么 | 本轮的臂/池 |
| --- | --- | --- | --- |
| **盲发牌（模型侧）** | `difficulty-abcd --arms=<池>/uniform` | **池子本身有多难**（无棋盘感知、无批次过滤、无回退） | `pool15` / `pool18`（新 id） |
| **分阶段发牌（模型侧）** | `difficulty-abcd --arms=<池>/staged` | 模型自带的分阶段发牌；⚠️ **只抽最初的 10 个形状**（§0.6） | `pool15` / `pool18` |
| **真实发牌器** | `deal-experiments --arms=<臂>` | **玩家实际会遇到什么**（`createGameSession()` 的 `dealDirector` + 求解器 + 回退阶梯） | 盲臂 **G–L**（可冻结）；盘面感知臂 **C/D**（跟随 src） |

⚠️ **交接单 §5 把 `staged` 当成"现行盘面感知发牌"是本次最大的口径误解**，
它导致 §5 第 2/3 步的两条命令在本轮**结构性无效**（差 0.00），也使通过线 ② 的阈值（40）定在了另一个口径上。
建议把 `difficulty-abcd` 的 `staged` 标签从"阶段发牌"补一句"仅覆盖 10 个原始形状"。

## 3. 形状几何与颜色

### 3.1 几何（规则测试断言，全部通过）

| 形状 | cells | 包围盒 | 最长直线段 | 空面落位数 | 能否自清线 | 一次最多补几条线 |
| --- | --- | --- | ---: | ---: | --- | ---: |
| `Cross 5` | 5 | 3×3 | 3 | **9** | 否 | **2**（横 3 + 竖 3 共用中心格） |
| `U 5` | 5 | 3×2 | 3 | **48** | 否 | 1 |
| `T 5` | 5 | 3×3 | 3 | **36** | 否 | **2** |

- **没有一个能自清**（最长 3 < 面宽 5）⇒ 不会重演 `Line 5` 的"放下必清线＝白送分"；
- **三个都能补线**（含 3 长直线段）⇒ 是"高压力 + 有回报"的件，不是纯压力件；
- **空面落位 9 / 36 / 48** 是难度分层的根源：同为 5 格件，`Cross 5` 落在 `Block 9` 那一档（也是 9），
  `T 5` 落在 `L 5` 那一档（36），`U 5` 最宽松（48）。规则测试按交接单 §2 的方法
  （**去重朝向 × 可行原点**）逐件钉死这三个数字，并在真实 `Board` 上复算了
  "`Cross 5` 的合法落位数 == `Block 9` 的合法落位数"。

两条都只需"人看一眼"就能判断，但**本轮不动它们**：它们属于渲染皮肤/整体配色重做，

## 7. 技术梯度：谁被惩罚、谁没被惩罚（通过线 ③）

交接单 §3.4/③ 要的是"**技术型更难**，不是运气型更短"：刻意留空间的打法不应一起崩。

3. **盲臂（§6）与真实发牌器（§8）必须分开读**：盲臂测的是"池子本身"（实收份额严格等于权重，§6.2），

## 9. 六条通过线：逐条判定

| 线 | 交接单阈值 | 实测 | 判定 |
| --- | --- | --- | --- |

## 12. 诚实性声明

- 本报告里**没有一个数字来自人类试玩**。`random` / `clear` / `noise` / `lookahead` / `space`
  都是机器人策略；`noise` 只是"典型玩家"的**代理**（75% 立即最优清线 + 25% 随机），不是人。
  通过线 ⑥ 因此**只能是待办**，不是已验。
- `stepCap = 600` 使均值成为**右删失**统计量；`greedy` / `lookahead` / `space` 大量触顶，
  它们的 p50 只能读作"下限"。所有受限均步都是删失感知的（`restrictedMeanSteps`）。
- Wilson / bootstrap 区间描述的是**蒙特卡洛不确定性**，不是模型误差，也不是真人置信区间。
- §4/§5 的 `difficulty-abcd` 数字来自**模型侧**（`difficulty-model.mjs` 自己实现棋盘/发牌），
  §6 的数字来自**真实台架**（`createGameSession()`）。两者不可混着读；本报告在每张表上都标了出处。
- §8 的前后对照**不是配对检验**（除 `random` 那一行）：after 侧与 before 侧都是**本轮亲自跑的**
  （before 在 `git worktree` 里 check out 到 `75c0572`，同一条命令、同一组 seed），
  所以两侧口径完全一致。`75c0572 → 0b6e995` 之间落进 main 的两个提交（并发编辑者）
  经 `git diff --stat` 核对**只改 `docs/` 与 `docs/Technical/assets/`**，不含任何 `src/` 或 `tools/`，
  因此不影响这个对照。但 `noise` 的逐局记录被同名默认 `--raw` 覆盖，只剩汇总表，
  因此 `noise` 只有点估计、没有配对区间。`random` 的配对检验是完整的（300 对）。
  已发布的 `tools/results/deal-experiments.summary.json`（`v0.9.0-p1.0`）只作为交叉印证：
  它给出的 `D/random` p50 = 23、`D/noise` p50 = 89，与本次 before 侧的 26 / 92 同量级
  （差异来自已发布版把四种打法放在同一次运行里，且它自己的注释说延迟被 45 路并行污染）。
- §3.3 的两个配色发现是**既有问题**，本报告只报告不修改。
- 本轮的扫描、配对与分析脚本留在 `%TEMP%`，**未入库**（沿用项目对一次性探针的惯例）；
  §3.1/§3.2 引用的口径数字已全部落成 `npm test` 里的硬断言，不需要脚本也能复算。
