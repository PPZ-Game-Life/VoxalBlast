## 3. 与 V4 并排比较：仍有的差异

1. **盘面是空的，V4 有彩色块**（默认开局即空盘，属 fixture 差异，不是渲染缺陷）。
2. **可见天空比 V4 少约 20 个点**：地平线解到 `edgeFromTop 0.390`，V4 的蓝天空带约占画面 45%。
3. **主盘占屏比 33.8% vs V4 约 38%**——§1.3 明确「不为了像参考图首先改 FOV / 相机角度」，
   这是**刻意保留的偏离**。
4. **两侧积木的数量与体量低于 V4**：竖屏下主盘占屏宽约 72%，两侧各只剩约 55px，装饰只能是贴着
   画框的窄条。**本轮把这条量化了**（模块新增 `decor` 诊断，逐件报出屏内盒子与位移）：

   ```text
   主盘禁带实测 [34,205,362,571] = 328px / 390px 画框宽（84%）
   ⇒ 两侧可用边距 左 34px / 右 28px
   arch-left   屏内宽 33px  位移 -54px      fore-left   屏内宽 33px  位移 -165px
   wall-left   屏内宽 34px  位移 -68px      fore-right  屏内宽 27px  位移 +138px
   ledge-left  屏内宽 33px  位移 -31px      wall-right  屏内宽 27px  位移 +58px
   ```

   **十件装饰里九件被避让推到只剩 23–34px 的贴边窄条**，位移最大的 `fore-left` 被推了 **165px**。
   §4.2 要的「两侧被画框裁切的**较大**积木」在竖屏下因此退化成不可读的窄条——
   **根因是 `layout.keepOutPaddingCssPx = 24` 本身**：主盘实心盒子已占 72%，两边各加 24px
   就把可用边距吃光了。这是**构图判断**，三条路都成立、方向要制作人定：
   ① 减小 padding（24 → 8 之类）换更宽的侧景；② 接受窄条；③ 按 §4.2「侧边缺空间就减少」
   把屏内宽低于某阈值的**整件剔掉**（少而完整，而不是多而残缺）。**本轮没改任何一个值。**
5. **接缝比配方给的背壳色更暗。** 390×844 正面横向扫描（y=340 与 y=400 两条独立扫线，x 90..300，
   读数一致）：格体亮度 **227**、缝底亮度 **33**，**缝比面暗 85%**（比值 0.147），
   半深宽度 **11px**（该视口格距 48.9px，约 22% 一格）。而配方给的背壳色是 `#243A4A`、亮度 **49**
   ——**缝比它自己规定的颜色还暗 33%**。
   **关键一条：这个视口上 SSAO 根本没开**（`getRenderQuality().lowPower` 在 ≤700px 处为真，
   且 `SHADOW_STYLE.lowPowerSSAO = false` ⇒ `useSSAO = false`；探针里 `tier: "low"`、`tierSpec.ssao: false`）。
   所以**手机的接缝变黑不是 SSAO 造成的**，§6.3-A 的排除法必须在**桌面档**（1440×900，`tier: "high"`、
   SSAO 开）上跑，不能拿手机这张图下结论。
   **§6.3-A 的 A/B 已做（本轮）**：1440×900、其余不变，`__voxalblastDev.ssao(false)` 把
   `ssaoEnabled` 从 `true` 切到 `false` 后重拍，两条扫线（y=300 / y=380，x 500..780）读数
   **逐位相同**——格体 227、缝 33、比值 0.147、半深宽 12/14px 两边一模一样。
   **结论：接缝的 85% 变暗与 AO 无关**，AO/接触暗化这条排查项到此排除；下一个变量是
   背壳色与相对光比（§6.3-D），不是 AO。
   另一条顺带得到的：桌面与手机的接缝比值都是 **0.147**、格体都是 227——它在两档之间是**比例不变**的。
   与 V4 的同口径对比仍未成立：直接扫概念图那一版扫线落在棋盘外轮廓上
   （缝底亮度 1、半深宽 152px），量的是黑描边不是内部接缝——**无效，不入结论**。
6. **软投影偏淡**：`opacity 0.20` / `heightFactor 0.11`，V4 的影子更重更宽。
7. **主页**：纪录牌与主/次按钮**已换新皮**（`14bedd2`，本会话复拍确认）。旧金冠＋花叶＋金边全部消失。
   仍有的差异：V4 的纪录牌顶的是一顶**大金冠**，本实现是一枚**深蓝描边的小皇冠**——语义对、体量小。
8. **彩漆比配方 albedo 更饱和**：少数通道被压到 0.40–0.78。A/B 显示这一抬升在**蓝色上把画面推向了 V4**
   （Δ26 对配方 albedo 的 Δ36），但**紫色明显不够蓝**（B 183 对 V4 的 240）。

## 11. 接缝为什么那么暗：反推它实际收到的光（§6.3-D 的前置）

AO 已被排除（§3 第 5 条）。下一步要动的是「光比还是背壳色」，所以先得知道这块暗色**是什么表面、
吃到什么光**。做法不靠猜：在**线性空间**算 `渲染值 / albedo`，得到该表面实际收到的光照。

| 表面 | 渲染 | albedo | 反推光照（线性 R/G/B） |
| --- | --- | --- | --- |
| 空格正面 | `#F2E9C8` | `#F4E4C0` | **0.981 / 1.050 / 1.096** |
| 接缝（若为背壳 `#243A4A`） | `#021E2B` | `#243A4A` | **0.034 / 0.307 / 0.353** |
| 接缝（若为轮廓 `#20334C`） | `#021E2B` | `#20334C` | **0.042 / 0.392 / 0.334** |

**两条结论：**

1. **受光面已经校准到位**：空格正面的反推光照是 **0.98 / 1.05 / 1.10**，三个通道都≈1 ——
   即它现在收到的就是"全强度白光"，这正是 §6.2 第 1 条要的「干净奶油」。C2 的补光已经打满。
2. **接缝只吃到冷光、而且极弱**：无论把它当背壳还是当轮廓，反推出来的光照都是**红通道 0.03–0.04、
   蓝通道 0.33–0.39**——红几乎为零。而键光（`#FFF4E4`）照到正面上是 0.98 的红。
   ⇒ **键光完全到不了缝里，缝只由冷色的半球天光照明。**

   它的色相也印证这一点：缝的通道比例是 **0.05 / 0.70 / 1.00**，比两个候选 albedo（红比 0.42–0.49）
   都要**冷得多**——不是某个 albedo 被整体压暗（那会保持比例），而是**换了一套光**。

**所以 §6.3-D 的落点是"光比"而不是"先几何"**：缝的亮度基本等于半球项的强度，
抬半球（或把地面反弹色去暖）能在不动受光面的前提下把缝提亮；抬背壳/轮廓 albedo 是另一条路。
**两条都没做**——它们都会改配色，按「口径你定、实现我落」，我先把读数摆在这里。

**一个仍未定的点**：缝到底属于**背壳**（`cubeBodyMaterial` 的 `#243A4A`）还是**方块轮廓**
（`edgeGeometry` 的 `#20334C`）。上表两种假设都列了，因为页面上没有"只关轮廓"或"只关背壳"的句柄，
分辨不了。真要做 §6.3-D，这个得先定——**否则改的是错的那一个**。

### 11.1 用几何算术回答它：11px 的暗带不可能是 2.4px 的缝

不需要句柄也能定这件事——把实测宽度和几何对上就行：

```text
格距                                 48.93 px（framing 实测 boardCellPx）
相邻两块的几何缝 = (1 - 0.95) 格     =  2.4 px
单块倒角半径 = 0.13 格               =  6.4 px；两块相对倒角合计 = 12.7 px
实测暗带半深宽                       = 11 px
⇒ 暗带 / 几何缝 = 4.5 倍；暗带 / 两块倒角合计 = 0.86 倍
```

**11px 是 2.4px 的 4.5 倍，却几乎正好等于两块相对倒角之和（0.86 倍）。** 所以：

- **暗带的"宽"来自方块自己的倒角，不是背壳。** 背壳只可能通过那 2.4px 的缝被看到，
  它撑不出 11px。
- 但**最暗的那一点**（`#021E2B`）是海军蓝——那是缝芯，量级上属于背壳/轮廓那种深蓝面。

于是 §6.2 第 3 条那句「不用浓黑 AO 扩大成橡胶隔条」里的**"厚"**，主要不是 AO、也不是背壳，
而是**两块倒角在掠射角下的暗部**。§6.3-D 因此有三个不同的把手，而且不是同一个东西：

| 想把什么改掉 | 把手 | §6.2 的优先级 |
| --- | --- | --- |
| 暗带**太宽**（11px） | 倒角的掠射响应（材料/光比），几何是最后手段 | §6.2 明写「**不先改几何缝隙**」 |
| 暗带**太黑**（缝芯 `#021E2B`） | 背壳/轮廓的 albedo，或抬半球把缝芯提亮 | §6.2「先查 hull、AO 和光比」 |
| 整体偏冷 | 半球/地面反弹的色温（反推光照红通道 0.03–0.04，见上表） | 同上 |

**三个都还没动**，因为都会改配色或几何；先说清"厚"和"黑"是两件事，免得动错了把手。

**`tuneMaterials` 帮不上这个分辨**：它只接受 `paint` / `wood` 两族的 `roughness` /
`envMapIntensity` / `metalness`，背壳是 `cubeBodyMaterial`、不在这两族里，所以调它分不出
"背壳 vs 倒角"。分辨是靠上面的宽度算术完成的。

### 12.1 删掉的是"第二块底板 / 第二套 glyph"的机制，不是像素

**保留了什么，为什么**：`border-width` / `border-image-width` / `border-image-repeat` 留着 —— 新皮肤只重声明
`border-image-source` + `-slice`，**给九宫格定尺的宽度仍然来自这里**，删了就是一次布局改动；

**没有做的**：本轮只删 **URL 类**声明（那才是"第二块底板/第二套 glyph"的机制）。被覆盖的
`text-shadow` / 颜色类声明仍在 `reference.css` 里（现 12 处，改动前 12 处），
**未删、本轮也未量化它们的重影风险** —— 不写成"旧样式已清干净"。

### 12.2 为什么这次的证据不能是截图

本轮开工时 `git status` 干净，中途**并行会话把 `src/rendering/floatingWorldScene.js` 改脏了**（1 行）。
结果：删除前后各跑一次全量门禁，**17 张图逐张不同**。天空对照区（1440×900 的 x400–700 / y10–100）在两轮之间
**61.7% 像素变化、maxDelta 88** —— 那就是并行会话的世界改动，跟 CSS 无关。所以"截图没变"这条路在本轮
**根本不成立**，需要换一种能归因的测法。

### 12.3 级联审计：把退役样式表原样注回去，看计算样式动不动

方法：在一次活页面会话里，把 `HEAD` 版的两份退役样式表（toy → reference，**顺序按 `main.js` 的 import 顺序**，
即 `floatingWorldUi.css` 之后）拼成一个 `<style>` 追加到 `<head>` 末尾 —— 那正是当年模块图注入它们的位置 ——
然后**逐元素逐属性**比较计算样式。

```text
元素数 342（注入前后一致）      比较属性 42 个（background-* / border-image-* / 盒模型 / 字体 / 变换…）
回放样式表解析出 270 条规则            计算样式差异：0
```

**0 处差异** ⇒ 这些声明全是纯级联输家，删掉它们**不可能改变任何一个被绘制的像素**。

审计本身先翻过两次车，一并记下（否则下一次还会踩）：
1. 一开始把整份 reference.css 排在 toy.css **前面**，两个旧文件之间等特异性的规则因此翻转，凭空造出 222 处差异；
   按 `main.js` 的真实 import 顺序（toy → reference）重排后降到 5 处。
2. 把 `<style>` 节点**先插进 DOM 再取快照**（内容是空的，取完快照再填）—— 直接插入会让每个元素的序号
   位移，342 行全部伪报"元素消失"。

### 12.4 它抓到的那 5 处差异是一个**真 bug**，不是噪声

5 处差异全在 `#app .score-plaque` 与 `#app .bottom-panel` 的
`background-position` / `background-size` / `background-repeat`：这两条规则**只声明了 `background-image`**，
另外三个 longhand 一直是**从那条即将被删的 `background:` 简写里继承来的**。
简写的 `background-image` 因特异性输给 `#app` 规则，**但它同时设置的三个 longhand 没有任何规则覆盖**，
于是它们一直悄悄生效。删掉简写之后，它们退回初值 —— 记分牌变成 `0% 0% / auto / repeat`，
**SVG 按固有尺寸平铺**。17 张视口截图没有一张能看出来，级联审计一眼看见。

修法就是 §5.2 要的写法：两条规则**各自把四个 longhand 说全**（`floatingWorldUi.css`）。

**修前 / 修后的画面证据**（1440×900 的 `desktop-board`，同一区域取样，step 2）：

| 区域 | r22→r23（删声明） | r23→r24（修 longhand） | **r22→r24（净效果）** | 噪声底 |
| --- | --- | --- | --- | --- |
| 记分牌**内部** | 12.4% / maxDelta 223 | 12.4% / maxDelta 223 | **0.00% / maxDelta 0** | 0.00% |
| 候选托盘 | 5.0% / maxDelta 205 | 5.0% / maxDelta 205 | **0.00% / maxDelta 0** | 0.00% |
| 记分牌（含圆角外的天） | 35.3% / maxDelta 223 | 36.6% / maxDelta 223 | 17.0% / maxDelta 88 | 0.00% |
| 天空对照（无 UI） | 22.5% / maxDelta 53 | 61.7% / maxDelta 113 | 61.7% / maxDelta 88 | 0.00% |

噪声底 = `artifacts/visual` 与 `artifacts/visual-r22`（同一构建的两次独立门禁）在同一区域的差：**0**，
所以门禁在这些区域是确定性的，"残余差异是抖动"这条解释不成立 —— 残余只能来自天空（对照区 61.7% 已经说明）。
**记分牌内部与候选托盘都回到逐位相同**，即：删声明的净效果，在 UI 上是零。

### 12.5 补了门禁，并证明它会红

`tools/floating-world-ui-paint.mjs` 新增「一块板必须自己声明它被画进哪个盒子」：对
`score-plaque` / `bottom-panel` / 工具瓦片 glyph 检查 `background-size` 不能是 `auto`、
`background-repeat` 不能是 `repeat`（**逐层**比较，因为工具瓦片是 glyph 叠板两层背景 —— 第一版按整串比较，
把它自己误报了一次）。

负控制（把 longhand 拆回 bug 状态再跑）：**门禁退出码 1**，报
`plate scale: score plaque paints … but declares no box (background-size: auto, background-repeat: repeat)`；
恢复后退出码 0、三块板全 `ok`。**门禁不是"永远绿"的摆设。**

### 13.3 缓存策略（§9.4 的「缓存策略」项，此前写着"无法在本地核对"）

`netlify.toml` 已经在仓库里，三项配置与实测清单对得上：

```toml
[build]  command = "npm run build"   publish = "dist"
/assets/*     -> public,max-age=31536000,immutable   # 构建产物里 4 个带内容哈希的资源
/index.html   -> no-cache                            # 入口永远回源
```

这与部署基线技能里的硬约束一致：**带 hash 的长期缓存、入口不缓存、无 hash 的资源不要手动永久缓存**。
实测清单是 **4 个带内容哈希**（`assets/index-*.js`、`index-*.css`、`dealWorker-*.js`）对 **24 个固定名**
（全部在 `/art/**`，跟随 SKU 名发布、不走 `/assets/*` 规则，正是"不要永久缓存"的那一类）。
`vite.config.js` 的 `base: './'` 让产物可以挂在子路径下 —— 这正是 `base` 与缓存规则要一起看的原因。

**SPA 重写：决定不加**，并写明理由。本作没有客户端路由（只有 `?` 查询参数），部署基线技能自己也写
「只有 `/` 的纯单页游戏非必须」；而 `/*` → `/index.html` 200 会把**真的 404**伪装成 200 + HTML，
对 WebGL 游戏反而更糟：资源缺失会表现为"脚本解析失败"而不是"这个文件不存在"。
